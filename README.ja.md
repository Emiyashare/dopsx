# dopsx：書類業務版の OpenSpec コマンド

dopsx は、会社設立、許認可申請、契約書、請求書、通知書などの書類業務を進めるための Claude Code プラグインです。OpenSpec の `/opsx` と同じ流れ（検討 → 計画 → 実行 → 検収 → アーカイブ）で進めます。内部では同じ openspec プログラムを使い、扱う対象をコードから書類に置き換えています。

`/opsx` はコードの変更向けに作られており、実行ではコードを書き換え、検収ではコードやテストを確認します。そのまま書類業務に使うと検収の方法が合わず、「お客様や役所の対応を待つ」状態もありません。dopsx はこれを補います。

- チェックリストの各項目に担当者を付けます：【我方】（当方）、【客户】（お客様）、【官方】（役所・銀行など）。
- 検収では書類そのものを確認します：成果物がそろっているか、名称・住所・日付・金額が書類間で一致しているか、記入漏れがないか。
- 確認済みの公式要件は、出典と確認日付きで要件ライブラリに蓄積され、次の同種の業務でそのまま使えます。

> dopsx は個人が開発した非公式のコミュニティ拡張で、OpenSpec およびその開発元（Fission AI）とは関係ありません。

## 前提条件

- Claude Code
- Node.js
- openspec プログラム 1.12.0（dopsx はこのバージョンでテストしています）

## インストール・更新・アンインストール

まず openspec プログラムをインストールします：

    npm install -g @fission-ai/openspec@1.12.0

次に、ターミナルでプラグインをインストールします：

    claude plugin marketplace add Emiyashare/dopsx
    claude plugin install dopsx@dopsx

Claude Code のセッション内で `/plugin marketplace add Emiyashare/dopsx`、続けて `/plugin install dopsx@dopsx` と入力しても構いません。インストール後、新しく開いたセッションで `/dopsx:*` の 12 個のコマンドが使えます。Windows、macOS、Linux（SSH で使うリモートホストを含む）のどれでも手順は同じで、インストールスクリプトを実行する必要はありません。

最新版への更新（更新後に新しく開いたセッションから反映されます）：

    claude plugin marketplace update dopsx
    claude plugin update dopsx@dopsx

アンインストール：

    claude plugin uninstall dopsx@dopsx

アンインストールで削除されるのはプラグイン本体だけです。作成済みの書類業務（`openspec/` と `documents/`）はそのまま残ります。

## 12 個のコマンド

**よく使うもの**

| コマンド | 内容 |
|---|---|
| `/dopsx:explore` | 検討：書類業務の中身を一緒に整理します。書類は作りません |
| `/dopsx:propose` | 業務を作成し、proposal・specs・design・tasks の 4 つの計画ファイルを一度に書きます |
| `/dopsx:apply` | 実行：チェックリストに沿って書類を作ります。お客様や役所の番になった項目では止まって待ちます |
| `/dopsx:verify` | 検収：チェックリストと成果物がそろっているか、各書類の名称・住所・日付が一致しているか、記入漏れ、出典が古くないか、要件ライブラリに個人情報が入っていないかを確認します |
| `/dopsx:archive` | アーカイブ：未決事項が残っている間はアーカイブしません。計画はアーカイブへ移し、成果物はその場に残します |

**計画を段階的に書く**

| コマンド | 内容 |
|---|---|
| `/dopsx:new` | 業務だけを作成します。計画は書かず、最初の計画ファイルの書き方を表示します |
| `/dopsx:continue` | 次の計画ファイルを 1 つずつ書きます。書いたものを確認してから先へ進めます |
| `/dopsx:ff` | 業務を作成して計画を一度に書きます。重要な情報が欠けているときだけ質問し、それ以外は妥当な仮定を置いて計画に書きます |

**その他**

| コマンド | 内容 |
|---|---|
| `/dopsx:update` | 途中で計画を修正し、4 つの計画ファイルの整合性を保ちます |
| `/dopsx:sync` | アーカイブせずに、確認済みの要件を先に要件ライブラリへ反映します |
| `/dopsx:bulk-archive` | 完了した複数の業務をまとめてアーカイブします。1 件ずつ同じ確認を行い、未決事項があるものはアーカイブしません。複数の業務で同じ要件の書き方が異なる場合は、確認日が新しいほうを採用します |
| `/dopsx:onboard` | 入門チュートリアル：今のフォルダにある小さな実際の書類業務を使い、解説付きで一連の流れを体験します |

コマンドを入力せず、やりたいことを普段の言葉で伝えても、Claude が対応するコマンドを選びます。

一般的な順序：

- 計画を一度に書く：`/dopsx:propose` → `/dopsx:apply`（お客様や役所を待ちながら何回かに分かれることがあります）→ `/dopsx:verify` → `/dopsx:archive`
- 1 つずつ確認しながら書く：`/dopsx:new` → `/dopsx:continue`（4 つの計画ファイルがそろうまで繰り返す）→ `/dopsx:apply` → `/dopsx:verify` → `/dopsx:archive`
- 始める前に整理したいときは `/dopsx:explore`。初めて使うときは、まず `/dopsx:onboard` を一度試してください

propose・new・continue・ff の違い：

| コマンド | 業務の作成 | 計画 | 不明点があるとき |
|---|---|---|---|
| propose | する | 4 つを一度に書く | 作る書類・提出先・期限に関わることは、先に確認してから書く |
| new | する | 書かない | — |
| continue | しない（既存の業務の続き） | 1 つずつ書く | 不明なら先に確認する |
| ff | する | 4 つを一度に書く | 重要な情報が欠けているときだけ質問し、それ以外は仮定して計画に書く |

4 つの計画ファイルの内容：

| ファイル | 内容 |
|---|---|
| proposal | 作る書類、提出先・送付先、期限、成果物の一覧、確認待ちの事項 |
| specs | 書類が満たすべき要件（公式の規定、お客様の要望、書式の要件）。各要件に出典と確認日を記載 |
| design | 進め方：使う公式様式、書式、署名の方法、提出方法、ファイル名、意図的な空欄、確認待ちの質問 |
| tasks | チェックリスト：各項目に担当者と完了の判断基準 |

確認が必要な要件のない簡単な書類（例：定型の請求書）では、specs は自動的に省略されます。

## フォルダ構成

最初の業務を始めたフォルダに、業務を作成するコマンド（`/dopsx:propose`、`/dopsx:new`、`/dopsx:ff`）が次の構成を自動で作ります。事前の準備は要りません。

```
<始めたフォルダ>
+-- openspec
|   +-- config.yaml          schema: doc-driven
|   +-- schemas/doc-driven   書類業務版のワークフロー定義（プラグインからコピー）
|   +-- specs                要件ライブラリ
|   +-- changes
|       +-- <業務名>          計画・下書き・経過資料
|       +-- archive          アーカイブ済みの計画
+-- documents
    +-- <業務名>              正式版の成果物（アーカイブ後もここに残ります）
```

- `openspec/schemas/doc-driven`：書類業務版のワークフロー定義。フォルダ作成時にプラグインからコピーされるので、フォルダを別のパソコンに移しても続けて使えます。進行中の業務は、開始時の版を使い続けます。
- `openspec/specs`：要件ライブラリ。確認済みの要件がここにまとまり、次の同種の業務でそのまま使えます
- `openspec/changes/<業務名>`：その業務の計画ファイル、下書き、経過資料
- `openspec/changes/archive`：アーカイブ済みの計画
- `documents/<業務名>`：正式版の成果物。アーカイブ後もその場に残り、計画のアーカイブ先を記した `过程记录.md`（経過記録）が追加されます

補足：

- サブフォルダで始めた場合は、上位フォルダにある既存の `openspec` をそのまま使い、重複して作りません。
- 要件ライブラリは `openspec` フォルダ単位です。同じフォルダの業務は要件ライブラリを共有し、別のフォルダで始めた業務はそれぞれ別になります。
- 正式版をお客様の会社フォルダにも保存したい場合は、「会社フォルダへコピー」をチェックリストの最後の項目にしてください。
- `/dopsx:apply` は元の資料（`documents` と `openspec` 以外のファイル）を書き換えません。変更が必要なファイルは、コピーしてから編集します。どうしても元のファイルを直接変更する場合は、先に確認します。
- そのフォルダがすでにコード用の OpenSpec プロジェクトである場合は、書類業務を作る前に確認します。

## 業務名のルール

openspec が受け付けるのは、英小文字・数字・ハイフンだけです。日本語、中国語、大文字、アンダースコアは使えません。

- 使える例：`sample-company-setup`、`2026-office-move`
- `documents` 配下のフォルダ名は業務名と同じです
- 書類そのもののファイル名には日本語や中国語を使えます。例：`documents/sample-company-setup/就任承諾書.docx`

## 担当者の表記

チェックリストの各項目は次の形で書かれます：`- [ ] 1.1 【我方】事项；完成判断：…`（担当者、内容、完了の判断基準）

- 【我方】（当方）：当方が行う項目。`/dopsx:apply` が実行します
- 【客户】（お客様）：お客様ご本人が行う項目。例：資料の提供、署名、来所
- 【官方】（役所など）：役所や銀行などの処理を待つ項目。例：受理、審査、証明書の発行

お客様や役所の項目が終わっていないときは、`/dopsx:apply` が止まり、誰の何を待っているかを知らせます。相手の対応が済んだら Claude に伝えてください。証憑を確認してからチェックを付けます。チェックの付いていない項目が残っている間は、`/dopsx:archive` も `/dopsx:bulk-archive` もアーカイブしません。

## 個人情報の扱い

- 要件ライブラリ（`openspec/specs`）には、規定そのもの、出典、確認日だけを書きます。お客様の氏名、住所、生年月日、証明書番号、口座などは書きません。
- アカウント、パスワード、暗証番号はどの計画ファイルにも書きません。チェックリストには「お客様ご本人が操作」または証憑の保管場所だけを書きます。
- お客様の氏名や住所は、業務フォルダ内の計画ファイルには書けます。これらのフォルダは自分のパソコンか非公開の保存先だけに置き、公開の Git リポジトリには push しないでください。
- 検収とアーカイブの際に、要件ライブラリに個人情報が混ざっていないか確認します。混ざっている場合は、反映もアーカイブもしません。

## 言語

計画ファイルのテンプレート、記入ガイド、担当者の表記（【我方】【客户】【官方】）は、現在中国語です。Claude はあなたの話す言語で応答し、計画の中身もあなたの言語で書きますが、テンプレートの見出しと担当者の表記は中国語のままです。

## ワークフロー定義だけを使う

Claude Code を使わず、自分の OpenSpec プロジェクトで doc-driven ワークフロー定義だけを使いたい場合は、OpenSpec コミュニティのワークフロー定義の慣例に従います。このリポジトリの `schemas/doc-driven/` をプロジェクトの `openspec/schemas/doc-driven/` にコピーし、`openspec/config.yaml` の `schema` を `doc-driven` に変更します（または業務の作成時に `--schema doc-driven` を付けます）。

確認方法：

    openspec schema which doc-driven
    openspec schema validate doc-driven

この方法で使えるのはワークフロー定義（4 つの計画ファイルのテンプレートと記入ガイド）だけです。お客様や役所の待機、書類の検収、アーカイブ前の確認といった動作は `/dopsx:*` コマンド側にあるため、Claude Code プラグインが必要です。

## 専門資格について

書類によっては、法律上、資格を持つ専門家（例：行政書士、司法書士、税理士、社会保険労務士）でなければ、代理で作成・提出できないものがあります。dopsx は計画の整理と書類作成のための道具で、誰がその書類を扱う資格を持つかは判断せず、法的助言も行いません。使う前にご自身で確認し、必要な場合は資格を持つ専門家に依頼してください。

## メンテナンス

**ワークフロー定義の変更**：`schemas/doc-driven/` では、記入ガイドとテンプレートの文言だけを変更します。proposal・specs・design・tasks の 4 つの計画ファイルの名前と順序は変えないでください。各フォルダに残っている古い版のコピーが新しい版のコマンドと一緒に使えるのは、このためです。

**既存のフォルダで新しいテンプレートを使う（任意）**：新しい版の `schemas/doc-driven/` で、そのフォルダの `openspec/schemas/doc-driven/` を上書きします。4 つの計画ファイルの名前と順序は変わらないので、進行中の業務には影響しません。

**openspec をアップグレードした後の確認手順**：

1. openspec をアップグレード：`npm install -g @fission-ai/openspec@latest`
2. 空の一時フォルダで、架空の小さな書類を使って `/dopsx:propose` → `/dopsx:apply` → `/dopsx:verify` → `/dopsx:archive` を一通り試します（途中でお客様の待機を 1 回含めます）。エラーがないこと、アーカイブ後に要件ライブラリに今回の要件が入っていることを確認します
3. 新しい OpenSpec の `/opsx` のワークフローと見比べ、dopsx に取り入れるべき改善がないか確認します。新しいワークフローが増えていれば、`skills/` にも対応する本文を追加して 1 対 1 の対応を保ちます
4. 3 つの説明文書と各スキルの `compatibility` に書かれたテスト済みの openspec バージョンを、新しい番号に更新します

**新しいバージョンの公開**：`skills/` や `schemas/` を変更したら、`.claude-plugin/plugin.json`、`.claude-plugin/marketplace.json`、各スキルの `metadata` のバージョン番号をそろえて上げ、`claude plugin validate . --strict` を実行し、3 つの説明文書を同じコミットで更新します。
